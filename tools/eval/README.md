# 构图算法离线评测

拍完照自动裁一刀（`AutoFrame.bestCrop`）到底有没有用？这组脚本给一套不需要真机、不需要模拟器的
离线基准：拿带主体掩膜的数据集，把像素或显著度网格喂给**端上同一份 Kotlin 算法代码**，
导出 TSV，再由 Python 算指标。

主结果是 **DUTS-TE 全量 5019 张**；另外用 **ECSSD 995 张**、**DUT-OMRON 5123 张** 做跨数据集交叉验证。
（2026-10-05：早期只用 200 张抽样，结论在扩到全量后被推翻一次 —— 见"200 张那版是抽样噪声"。）

跑的是 app 主源集里那几个类本身（`AutoFrame`、`SaliencyMath`），不是另写一遍 Python 版算法 ——
否则测的是复刻品，不是线上代码。

## 跑一遍

```bash
# 1) 准备数据：下 DUTS-TE，--all 用全量 5019 张（不加 --all 默认抽 200 张）
python tools/eval/prepare_data.py --all

# 2) 显著度从哪来，二选一
python tools/eval/pack_pixels.py --manifest work/manifest.tsv --out-dir work   # 规则算法：原始像素
python tools/eval/model_grid.py --manifest work/manifest.tsv --out-dir work \
    --model app/src/main/assets/u2netp.onnx                                    # u2netp：64x48 显著度网格

# 3) 跑 Kotlin 侧算法（必须先 cd 到仓库根，否则 gradle 找不到 build）
export JAVA_HOME=/path/to/jdk17 ANDROID_HOME=/path/to/android-sdk
export EVAL_MANIFEST=work/grids_manifest.tsv
export EVAL_GRID=work/grids.bin               # 规则口径改成 EVAL_PIXELS=work/pixels.bin
export EVAL_ASPECT=src EVAL_OUT=work/harness_model_src.tsv
./gradlew :app:testDebugUnitTest --tests 'cn.yege.dshcam.EvalHarnessTest' --rerun
# 换比例：EVAL_ASPECT=1 或 0.75；换门槛口径：EVAL_GATE/EVAL_GATE_REL

# 4) 算指标、出 markdown/json 报告
python tools/eval/run_eval.py --manifest work/manifest.tsv \
    --harness work/harness_model_src.tsv --label model-src --aspect src

# 5) 多份报告并排成一张表（--reports 支持通配符，顺序即行序）
python tools/eval/compare_reports.py --reports 'work/report_*.json' \
    --labels 模型/src 模型/1:1 模型/3:4 规则/src 规则/1:1 规则/3:4 \
    --title 'DUTS-TE 全量 5019 张' --out-md work/compare.md

# 6) 自检（不用真机）
python tools/eval/metrics.py             # metrics self-test OK
python tools/eval/test_metrics.py        # 12 个用例
```

Windows PowerShell 把 `export A=B` 换成 `$env:A='B'`。`--rerun` 不能省：不加的话 gradle 会
判定测试 UP-TO-DATE，直接跳过、不产出文件。

**跨数据集**：`prepare_data.py` 只认 DUTS 那套 zip 目录结构；外部数据集（ECSSD、DUT-OMRON）
各自要有 `manifest.tsv`（`image<TAB>mask`，绝对路径），流程一样，只要第 3~4 步的
`--manifest` / `EVAL_MANIFEST` 指向那个数据集的清单。

### EVAL_* 环境变量

| 变量 | 作用 |
| --- | --- |
| `EVAL_MANIFEST` | 清单：`index<TAB>image<TAB>w<TAB>h`，多余列忽略，可带表头 |
| `EVAL_PIXELS` | 原始像素，每张 64x48 个大端 int32（12288 字节） |
| `EVAL_GRID` | 显著度网格，每张 64x48 个大端 float32（12288 字节）；**给了它就忽略 `EVAL_PIXELS`** |
| `EVAL_ASPECT` | `src`（默认，保持原图比例只变焦）或正数（`1`、`0.75`）；写错直接抛异常，不悄悄退回 src |
| `EVAL_GATE` | 动剪刀门槛的口径：`abs`（默认，绝对分差）/ `range`（候选分动态范围的比例）/ `headroom`（离满分还差多少的比例） |
| `EVAL_GATE_REL` | 门槛值，默认 `AutoFrame.ABS_GATE_MARGIN`（0.05）；**必须 > 0**，想测"永远采纳"给个极小值（0.0001），给 0 会抛异常 |
| `EVAL_ANCHOR` | 候选锚点数（正整数）；不设＝线上现在的 `wk/16` 步长 |
| `EVAL_OUT` | 输出 TSV 路径 |

后三个不设时就是线上现在的行为（`ABS` / `0.05` / `wk/16` 步长），所以只跑常规对照不用管它们。

harness 结束时会把一行 `[eval-harness] total=5019 ok=5019 skipped=1584 errors=0 aspect=src gate=ABS/0.05 anchor=legacy avg_crop_us=980`
打到 stdout，但 gradle `--console=plain` 不显示它 —— 要从 `app/build/test-results/testDebugUnitTest/TEST-cn.yege.dshcam.EvalHarnessTest.xml`
的 `<system-out>` 里翻。每次 `--rerun` 都会覆盖这个 XML，想留就当场抄。

不设 `EVAL_*` 时这个测试自己 `Assume` 跳过，常规 `gradlew test` 里只记一条 skipped。

**为什么像素要外部喂**：Android 模块的单测拿 `android.jar` 当编译期 JDK，`java.desktop` 整个包不在，
`javax.imageio` / `java.awt` 全都用不了，Kotlin 侧读不了 JPEG。所以解码、缩放放 Python，
Kotlin 只管跑算法。

## 指标

| 指标 | 含义 |
| --- | --- |
| 保留率 `kept_ratio` | 裁完框里还剩多少主体掩膜像素，1.0 = 一个像素没切 |
| 密度 `density` | 框内主体像素占比，越高说明框得越紧 |
| 居中裁剪 `center` | 同样尺寸、位置居中的框（最朴素的基线） |
| 最优位置 `optimal` | 同尺寸下平移到掩膜最优位置的上界 |
| `capture_ratio` | Σ(算法−居中)/Σ(最优−居中)，只在最优高于居中的图上算 |
| 三分点距离 | 主体质心到最近三分交点的距离（归一化，交点为 0，正中心约 0.2357 最远） |
| 摆正中比例 | 主体质心离裁剪框中心 5% 以内 |
| 切到主体比例 | 框内留下不到 99% 的主体像素 |
| 主体损失 | 1 − 保留率，即被裁掉的主体像素比例；报告里按 >1% / >5% / >10% / >20% / >50% 分档给曲线 |

保留率单看会骗人：整图不裁拿 1.0000，但密度只有 0.14。所以两组指标必须并列看 ——
保留率回答"有没有把主体切掉"，三分点距离才回答"主体摆得正不正"。

`capture_ratio` 也别单看：它的分母是"最优 − 居中"这个可提升空间，空间小的数据集上（ECSSD 的
src 口径只有 1.2 个百分点）它会放大成 −70% 这种数字。**跨数据集比大小要看"算法 − 居中"的原始差值**，
capture 只用来在同一数据集内比较不同口径。

### 200 张那版是抽样噪声

早期只抽了 200 张，报的是"模型/src 保留率 0.9777 > 居中 0.9751，三个比例都赢"。扩到全量 5019 张后
符号反过来（0.9727 < 0.9785）。配对重算说得很清楚：

- 全量 5019 张：均值 **−0.00587**，中位 0，标准差 0.0592，配对 **t = −7.03**；算法更好 637 / 打平 2794 / 居中更好 1588。
- 同样 src 口径、只取当初那 200 张：均值 **+0.00262，t = +0.50**（不显著）。

也就是说 200 张那次的正号本来就在抛硬币区间里。**样本量不够时别下结论** —— 同理，美学那节
0.006 分这种量级的差在 140 对里也分辨不出来（要 ~1300 对）。

## 跨数据集交叉验证

同一套 harness、同一套指标，换成两个外部数据集（都不在 DUTS 的训练/测试池里）：
**ECSSD**（CUHK hsaliency `data/ECSSD/images.zip` + `ground_truth_mask.zip`，剔除 5 张短边 < 200 的）
和 **DUT-OMRON**（`saliencydetection.net` 的 `DUT-OMRON-image.zip` + `DUT-OMRON-gt-pixelwise.zip.zip`，
剔除 45 张短边 < 200 或前景 < 0.2% 的）。
模型口径 src 的逐图配对差异（算法保留率 − 居中保留率）：

| 数据集 | 图数 | 算法 | 居中 | 差值 | 配对 t | 胜/平/负 | 三分距 算法/居中 | 摆正中 算法/居中 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| DUTS-TE | 5019 | 0.9727 | 0.9785 | **−0.0059** | −7.03 | 637/2794/1588 | 0.0951 / 0.1467 | 3.5% / 13.0% |
| ECSSD | 995 | 0.9703 | 0.9839 | **−0.0136** | −9.96 | 113/483/399 | 0.0907 / 0.1473 | 4.0% / 15.9% |
| DUT-OMRON | 5123 | 0.9704 | 0.9727 | **−0.0023** | −2.02 | 701/3012/1410 | 0.1026 / 0.1514 | 2.9% / 11.4% |

三个数据集上是同一幅图景，中位数都恰好是 0（大多数图两者打平）：

1. **src 口径：算法比同尺寸居中裁剪多切一点点主体**，0.23~1.36 个百分点，方向一致、都显著（OMRON 边缘）。
   极端个案也在三个集上都出现：保留率 = 0（主体被整个切掉）的图，DUTS 2 张、OMRON 7 张、ECSSD 0 张，
   居中裁剪一张都没有。最惨一例 `sun_aibkalhfyvjqfjvq.jpg`：算法 0.0632，居中 1.0000。
   这类图的根因在 u2netp 显著度跟掩膜标注不一致（框跟着错的显著度跑了），不是搜框逻辑本身。
2. **构图改善稳定复现**：三分点距离三个集都降 30%~38%，摆正中比例从 11%~16% 降到 3%~4%。
3. **换比例时保留率优势复现**：1:1 差值 +0.0075 / −0.0011 / +0.0117（基本打平到小赢），
   3:4 差值 +0.0243 / +0.0158 / +0.0364（三个集全赢），且 >20% 深切比例都更低。
4. **规则兜底是短板这件事也复现**：src 口径不裁比例 63.4% / 63.3% / 64.7%（图基本没动刀），
   保留率差值 −0.0064 / −0.0092 / −0.0038，全都在居中基线之下。

结论：**"保持原比例只变焦时，算法用一点点主体安全换构图"这件事是真的、可复现的；但"主体更安全"不成立** ——
要得到那个三分点构图，算法平均多切 0.6~1.4 个百分点的主体。换比例时则是净赚。

## 两个可调旋钮（全量 5019 张复核）

`bestCrop` 动剪刀的判据原来是写死的绝对分差 `bestScore >= base + 0.05`（`AutoFrame.kt:589`）。
加了 `gate` / `gateRel` / `anchorCount` 三个参数，默认值等于旧行为。全量复核（模型 src）：

| 门槛口径 | 不裁比例 | 算法保留率 | 居中保留率 | 提升捕获 | 平均主体损失 | >10% 深切 | 三分点距离 | 摆正中 | 平均裁剪面积 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ABS 0.0001（永远采纳） | 5.8% | 0.9614 | 0.9662 | −1.9% | 3.86% | 12.2% | 0.0883 | 1.1% | 0.693 |
| **ABS 0.05（线上现状）** | 31.6% | 0.9727 | 0.9785 | −11.4% | 2.73% | 8.5% | 0.0951 | 3.5% | 0.752 |
| RANGE 0.10 | 27.9% | 0.9699 | 0.9810 | −48.5% | 3.01% | 9.5% | 0.0925 | 2.5% | 0.747 |
| RANGE 0.30 | 75.2% | 0.9904 | 0.9959 | −111.3% | 0.96% | 2.8% | 0.1182 | 6.4% | 0.907 |
| ABS 0.05 + 锚点 12 | 32.8% | 0.9730 | 0.9791 | −12.8% | 2.70% | 8.4% | 0.0970 | 3.7% | 0.759 |

1. **相对门槛（RANGE）更差，全量复核后依然成立。** RANGE 0.10 的不裁比例跟 ABS 0.05 接近
   （27.9% vs 31.6%），但"算法 − 居中"从 −0.0059 掉到 −0.0111，平均主体损失从 2.73% 涨到 3.01%。
   机制是候选分动态范围小＝这张图本来就没什么构图信号，低门槛反倒让它先动剪刀，专挑难的图裁。
   RANGE 0.30 走向另一个极端（75% 的图直接不裁），capture 变成 −111%。**要定的只是"门槛取多少"，
   不是"用哪种口径"。**
2. **ABS 0.05 是一笔明确的取舍，不是白赚。** 把门槛压到 0（永远采纳）能换来更贴三分点的构图
   （0.0883 vs 0.0951，摆正中 1.1% vs 3.5%）和更高的平均紧凑度（裁剪面积 0.693 vs 0.752），
   代价是：保留率掉 1.1 个点、平均主体损失从 2.73% 涨到 3.86%、>10% 深切从 8.5% 涨到 12.2%。
   **这道门槛挡住的正是"裁了构图更好、但要切主体"的犹豫案例。**
3. **锚点量化到 12 个：1.94 倍速，指标基本不动。** 候选从 `wk/16` 步长的 255 个降到 93 个
   （−63.5%），`bestCrop` 单图耗时 **980 µs → 504 µs**（同一天同一台机器，全量 5019 张的平均）；
   动剪刀的图从 1584 张变成 1645 张（1.2% 的图改了决定），聚合指标几乎不动
   （保留率 0.9727 → 0.9730，三分点距离 0.0951 → 0.0970，平均损失 2.73% → 2.70%）。
   64x48 的网格上再密也只是在重复采样同一个局部极大值。默认关着（`anchorCount = 0` 仍是旧步长）。

## 第二指标：换个"眼睛"看——美学模型也说不出哪种裁法更好看

保留率、三分点距离都是几何指标，能证明"主体没被切掉、摆得更靠三分点"，证明不了照片变好看。
所以又接了两个在 AVA 上训过的美学打分模型，做同尺寸配对比较（算法框 vs 居中框）。

模型不入库，自己下（CPU 跑，onnxruntime，不需要 torch）：

| 模型 | 来源 | 大小 | AVA 排序相关 |
| --- | --- | --- | --- |
| TOPIQ-IAA ResNet50 | `cromsc/topiq-iaa-res50` → `topiq_iaa_res50.onnx` | 267 MB | PLCC 0.737 / SRCC 0.7359 |
| NIMA MobileNet | `cromsc/nima-mobilenet-aesthetic` → `nima_mobilenet_aesthetic.onnx` | 12.3 MB | 约 0.717（VGG16 版口径） |

```powershell
python tools/eval/export_crops.py --manifest <work>\manifest.tsv --harness <work>\harness_model_src.tsv --out-dir <work>\crops_trim --only-cropped
python tools/eval/aesthetic_score.py --pairs <work>\crops_trim\pairs.tsv --model-dir <模型目录> --models topiq,nima --full
# pref_eval 每次只吃一个模型的分数文件（index<TAB>pred_score<TAB>center_score），两个模型跑两次
python tools/eval/pref_eval.py --pairs <work>\crops_trim\pairs.tsv --scores <work>\crops_trim\scores_topiq.tsv --label topiq --out-json <work>\crops_trim\pref_topiq.json --out-md <work>\crops_trim\pref_topiq.md
```

两模型合计 58 ms/图（TOPIQ 49.8 ms、NIMA 2.3 ms）；5019 张里真正裁过的 3435 对（`--only-cropped`
把"没动刀"的 1584 张滤掉），跑完 779 秒。`export_crops.py --sheet 1` 会另外拼一张对比图方便肉眼看。

结果（model-src 口径，3435 对）：

| 模型 | 算法均分 | 居中均分 | 胜/平/负 | 平均分差 | 符号检验 p | 分差 σ | 95% CI |
| --- | --- | --- | --- | --- | --- | --- | --- |
| TOPIQ-IAA | 4.462 | 4.467 | 1670/0/1765 | −0.0045 | 0.1087 | 0.129 | ±0.004 |
| NIMA MobileNet | 3.899 | 3.906 | 1613/0/1822 | −0.0074 | 0.0004 | 0.126 | ±0.004 |

**两个美学模型都看不出算法裁剪比居中裁剪更好看。** 平均差 0.005~0.007 分（量程 1~10，约 0.1%），
NIMA 那一档虽然符号检验显著（p=0.0004），但方向是**略负**——不构成"算法更好看"的证据。

- 3435 对的功效足够分辨 0.004 分（0.08%）级别的差异了；点估计仍然贴在零附近，不是"没测出来"。
- 反过来问"算法把主体推近三分点了，美学分涨了吗"（200 张口径的相关性分析）：分差与构图改善的
  pearson 只有 +0.069（TOPIQ）、−0.224（NIMA），**美学分没奖励这个改善**。
- 唯一略正面的信号在"动得多"那档：与居中框差得较多的 27 对，TOPIQ +0.0175、18/27 胜（n 太小）。
- 顺手排除一个假象：**"裁一刀会掉分"是预处理造成的**。同样 40 对，直接拉伸到 384×384 时
  "算法 − 原图"是 −0.248（1/40 为正）；改成保比缩放 + 填灰边后变成 +0.157（34/40 为正）。
  形变一换符号就翻，所以整图对比不下结论，只用同尺寸配对比较。

这一节的局限：

- GAIC 那篇论文明确反对拿整图训练的美学分类器评图内裁剪（他们那条"什么都不裁的 Baseline_N IoU 反而最高"
  就是同类的坑）。这里当"第二意见"用，不当判据。
- TOPIQ 对 resize 敏感：同图拉伸 / BICUBIC / 短边加中心裁剪，分差最多 0.5 分，是上面那个分差的 60 倍。
  全程锁死"直接拉伸 + BILINEAR"，绝对分不能跨预处理比。
- 两个模型都在 AVA 上训，相互相关 0.722，算不上真正独立的两票。
- 定稿口径：**几何指标说"主体更靠三分点、但要切一点主体"，美学模型说"看不出更好看"。
  两者不矛盾——前者是构图规则，后者是人群偏好。**

## 结论

1. **模型显著度让这套算法值钱，但赚的是构图，不是主体安全。** 全量 5019 张上，src 口径算法
   平均只留 75.2% 的画面，把三分点距离从 0.1467 压到 0.0951（−35%），摆正中的比例从 13.0% 降到 3.5%；
   代价是保留率 0.9727 < 居中裁剪 0.9785（配对 t=−7.03）。换比例（1:1 / 3:4）时构图和保留率
   一起赢（3:4 保留率 0.8856 vs 0.8613，平均主体损失 11.44% vs 13.87%）。
   **一句话：算法在做"更激进的三分点构图"，这个取舍是全量数据上量出来的，不是白拿的。**
2. **规则兜底显著度是这条链路的短板。** 换成 `salienceFromArgb`，src 口径 63.4% 的图直接不裁
   （规则图峰值太弥散，过不去"bestScore ≥ base + 0.05"那道门槛），裁了的也保不住主体
   （0.9796 vs 居中 0.9860）；换比例更差（1:1 −0.0201、3:4 −0.0418）。三个数据集上都是这个模式。
   **要提升自动构图，先提升兜底显著度，而不是改搜框逻辑。**
3. **"切到主体"这个数字要配损失分档一起看。** src 口径算法切到主体的图更多（31.1% vs 23.6%），
   深切（>10%）也更多（8.5% vs 7.4%）；但换比例时反过来，3:4 的平均损失、p90、>10% / >20% 几档
   算法都更好。判据是"框内留下 < 99% 的主体像素"，掩膜边缘擦掉一点也算，所以单看这个比例会
   把算法判得比实际更粗暴 —— 但也不能像 200 张那版那样反过来说"算法深切更少"，全量不支持。
4. **还有一类硬失败：主体被整个切掉。** 保留率 = 0 的图，DUTS 2 张、DUT-OMRON 7 张，居中裁剪 0 张。
   根因是 u2netp 显著度跟掩膜标注打架时框跟着错的显著度跑了。要不要加"框内显著度总量太低就退回不裁"
   的保险，值得单独评估。
5. **两个旋钮：门槛别改成相对口径，候选锚点可以放心砍到 12 个。** 前者全量复核更差（RANGE 0.10
   平均损失 3.01% vs ABS 0.05 的 2.73%），后者 1.94 倍速、指标基本不动。默认值都还是旧行为。
6. **"更好看"这件事，这批评测证明不了。** 两个 AVA 美学模型在 3435 对上给的平均分差是
   −0.005 / −0.007 分，方向略微不利。要下"构图更好看"的结论得靠人评（成对偏好），
   这批评测只能给"几何上更靠三分点、代价是多切一点主体"。

## 局限（别把上面的数字用过头）

- DUTS-TE / ECSSD / DUT-OMRON 都是**显著性**数据集，掩膜标注的是"主体在哪"，不是"这张照片构图好不好"。
  它们能证明"没把主体裁掉、主体摆得更靠三分点"，**证明不了照片更好看**。三个集都是
  "一张图一个突出主体"的分布，多主体、无人像特写的场景没覆盖。
- 跨数据集只做了三个（PASCAL-S 官方源当时 502/SSL 挂了被跳过，DIS5K 单文件太大放弃），
  而且都是有掩膜标注的显著性数据集，选择偏差还在。
- 网格只有 64x48，框的宽高比与请求值最多差约 1%（网格量化）。算法、居中基线、最优上界都在
  同一套网格上取框，所以三方对比公平，但绝对值别当精确值读。
- harness 不处理 EXIF 方向（这三个数据集都没有方向标记），也不走线上 `GRID_PEAK_GATE = 0.75` 那道
  "没主体就不另存"的闸；这批评测每张都有主体，那道闸不影响结论。
- 掩膜本身有标注噪声（边缘像素、细小主体），"切到主体"的 1% 容差也因此偏敏感。主体损失分布表就是
  为了把这个敏感度显式化：>1% 那列别单读，和 >10% / >20% 两列一起看。
- `avg_crop_us` 是单次 JVM 内的平均，含 JIT 预热，只能做同一次运行内的相对比较
  （980 µs vs 504 µs 是同一天同一台机器跑出来的）。
- `pack_pixels.py` 用 `PIL` 双线性缩放；端上用 `Bitmap.createScaledBitmap(..., true)`。
  大比例缩小时两者接近，但不是逐位一致。
