# 构图算法离线评测

拍完照自动裁一刀（`AutoFrame.bestCrop`）到底有没有用？这组脚本给一套不需要真机、不需要模拟器的
离线基准：拿 DUTS-TE 里 200 张带主体掩膜的图，把像素或显著度网格喂给**端上同一份 Kotlin 算法代码**，
导出 TSV，再由 Python 算指标。

跑的是 app 主源集里那几个类本身（`AutoFrame`、`SaliencyMath`），不是另写一遍 Python 版算法 ——
否则测的是复刻品，不是线上代码。

## 跑一遍

```bash
# 1) 准备数据：下 DUTS-TE，抽样 200 张，产出 work/manifest.tsv（image<TAB>mask）
python tools/eval/prepare_data.py --limit 200

# 2) 显著度从哪来，二选一
python tools/eval/pack_pixels.py --manifest work/manifest.tsv --out-dir work   # 规则算法：原始像素
python tools/eval/model_grid.py --manifest work/manifest.tsv --out-dir work   # u2netp：64x48 显著度网格

# 3) 跑 Kotlin 侧算法（必须先 cd 到仓库根，否则 gradle 找不到 build）
export JAVA_HOME=/path/to/jdk17 ANDROID_HOME=/path/to/android-sdk
export EVAL_MANIFEST=work/pixels_manifest.tsv
export EVAL_PIXELS=work/pixels.bin            # 用 EVAL_GRID 时改成 work/grids.bin
export EVAL_OUT=work/harness_src.tsv
./gradlew :app:testDebugUnitTest --tests 'cn.yege.dshcam.EvalHarnessTest' --rerun

# 4) 算指标、出 markdown/json 报告
python tools/eval/run_eval.py --manifest work/manifest.tsv --harness work/harness_src.tsv --label rule-src

# 5) 自检（不用真机）
python tools/eval/metrics.py             # metrics self-test OK
python tools/eval/test_metrics.py        # 12 个用例
```

Windows PowerShell 把 `export A=B` 换成 `$env:A='B'`。`--rerun` 不能省：不加的话 gradle 会
判定测试 UP-TO-DATE，直接跳过、不产出文件。

### EVAL_* 环境变量

| 变量 | 作用 |
| --- | --- |
| `EVAL_MANIFEST` | 清单：`index<TAB>image<TAB>w<TAB>h`，多余列忽略，可带表头 |
| `EVAL_PIXELS` | 原始像素，每张 64x48 个大端 int32（12288 字节） |
| `EVAL_GRID` | 显著度网格，每张 64x48 个大端 float32（12288 字节）；**给了它就忽略 `EVAL_PIXELS`** |
| `EVAL_ASPECT` | `src`（默认，保持原图比例只变焦）或正数（`1`、`0.75`）；写错直接抛异常，不悄悄退回 src |
| `EVAL_GATE` | 动剪刀门槛的口径：`abs`（默认，绝对分差）/ `range`（候选分动态范围的比例）/ `headroom`（离满分还差多少的比例） |
| `EVAL_GATE_REL` | 门槛值，默认 `AutoFrame.ABS_GATE_MARGIN`（0.05） |
| `EVAL_ANCHOR` | 候选锚点数（正整数）；不设＝线上现在的 `wk/16` 步长 |
| `EVAL_OUT` | 输出 TSV 路径 |

后三个不设时就是线上现在的行为（`ABS` / `0.05` / `wk/16` 步长），所以只跑常规对照不用管它们。

harness 结束时会把一行 `[eval-harness] total=200 ok=200 ... aspect=src gate=ABS/0.05 anchor=12 avg_crop_us=564`
打到 stdout，但 gradle `--console=plain` 不显示它 —— 要从 `app/build/test-results/testDebugUnitTest/TEST-cn.yege.dshcam.EvalHarnessTest.xml`
的 `<system-out>` 里翻。

不设 `EVAL_*` 时这个测试自己 `Assume` 跳过，常规 `gradlew test` 里只记一条 skipped。

**为什么像素要外部喂**：Android 模块的单测拿 `android.jar` 当编译期 JDK，`java.desktop` 整个包不在，
`javax.imageio` / `java.awt` 全都用不了，Kotlin 侧读不了 JPEG。所以解码、缩放放 Python，
Kotlin 只管跑算法。

## 指标

| 指标 | 含义 |
| --- | --- |
| 保留率 `kept_ratio` | 裁完框里还剩多少主体掩膜像素，1.0 = 一个像素没切 |
| 密度 `density` | 框内主体像素占比，越高说明框得越紧 |
| 居中裁剪 `center` | 同样尺寸、位置居中的框（最朴素的基线） |
| 最优位置 `optimal` | 同尺寸下平移到掩膜最优位置的上界 |
| `capture_ratio` | Σ(算法−居中)/Σ(最优−居中)，只在最优高于居中的图上算 |
| 三分点距离 | 主体质心到最近三分交点的距离（归一化，交点为 0，正中心约 0.2357 最远） |
| 摆正中比例 | 主体质心离裁剪框中心 5% 以内 |
| 切到主体比例 | 框内留下不到 99% 的主体像素 |
| 主体损失 | 1 − 保留率，即被裁掉的主体像素比例；报告里按 >1% / >5% / >10% / >20% / >50% 分档给曲线 |

保留率单看会骗人：整图不裁拿 1.0000，但密度只有 0.1413。所以两组指标必须并列看 ——
保留率回答"有没有把主体切掉"，三分点距离才回答"主体摆得正不正"。

## 两个可调旋钮的实测（2026-10-05，模型口径 src，200 张）

`bestCrop` 动剪刀的判据原来是写死的绝对分差 `bestScore >= base + 0.05`（`AutoFrame.kt:589`）。
现在加了 `gate` / `gateRel` / `anchorCount` 三个参数，默认值等于旧行为，线上没变。扫描结果：

| 门槛口径 | 不裁比例 | 算法保留率 | 居中保留率 | 提升捕获 | 切到主体 | 平均主体损失 |
| --- | --- | --- | --- | --- | --- | --- |
| ABS 0（永远采纳） | 4.0% | 0.9649 | 0.9571 | +38.6% | 46.0% | 3.51% |
| ABS 0.01 | 7.0% | 0.9656 | 0.9578 | +39.1% | 44.0% | 3.44% |
| ABS 0.02 | 12.0% | 0.9670 | 0.9606 | +36.8% | 41.0% | 3.30% |
| ABS 0.03 | 15.5% | 0.9698 | 0.9636 | +39.4% | 39.0% | 3.02% |
| **ABS 0.05（线上现状）** | 30.0% | 0.9777 | 0.9751 | +39.7% | 31.0% | **2.23%** |
| RANGE 0.10 | 28.0% | 0.9721 | 0.9777 | **+1.0%** | 36.0% | — |
| RANGE 0.30 | 72.5% | 0.9935 | 0.9970 | **−62.2%** | 13.0% | — |
| RANGE 0.50 | 100%（完全不裁） | 1.0000 | 1.0000 | 0 | 0 | — |
| HEADROOM 0.10 | 14.0% | 0.9690 | 0.9650 | +34.3% | 40.0% | — |
| HEADROOM 0.20 | 30.5% | 0.9782 | 0.9784 | +31.1% | 31.0% | — |
| HEADROOM 0.30 | 47.0% | 0.9831 | 0.9863 | +18.4% | 24.0% | — |

1. **相对门槛既不更"校准"，也不更好用。** 直觉是"绝对分差在不同照片上不等价，改成相对动态范围的比例"
   会更公平，实测相反：RANGE 0.10 在跟 ABS 0.05 差不多的不裁率（28% vs 30%）下，提升捕获只有 +1.0%
   （ABS 是 +39.7%）。机制是候选分动态范围小＝这张图本来就没什么构图信号，低门槛反倒让它先动剪刀，
   等于专挑难的图裁。HEADROOM 那一列从 0.10 到 0.30 是一条平滑的保守化曲线，也追不上 ABS 0.05 的捕获率。
   **结论：这个旋钮真正要定的只是"门槛取多少"，不是"用哪种口径"。**
2. **ABS 0.05 正好卡在拐点上。** 门槛从 0.05 降到 0 换来的是：多裁 26 个百分点的图，保留率掉 1.3 个点，
   平均主体损失从 2.23% 涨到 3.51%，提升捕获没变好（+38.6% vs +39.7%）。也就是说这道门槛确实在干活，
   它挡掉的是"裁了也不赚、但会切主体"的那些犹豫案例。
3. **锚点量化白拿 1.8 倍速。** 候选锚点从线上现在的 `wk/16` 步长（255 个候选/图）量化到 12 个锚点
   （93 个候选/图，−63.5%），质量指标几乎不动（保留率 0.9777 vs 0.9777，三分点距离 0.0988 vs 0.0982，
   平均主体损失 2.23% vs 2.23%），`bestCrop` 单图耗时从 1002 µs（两次跑 1002/997）降到 564 µs。
   64x48 的网格上再密也只是在重复采样同一个局部极大值。默认关着（`anchorCount = 0` 仍是旧步长）。

复现命令（六份报告都在 `work/`，`harness_*.tsv` 是原始逐图输出，`report_*.{md,json}` 是汇总）。
模型口径换比例只要改 `EVAL_ASPECT` 和输出名：

```bash

```

## 结论

1. **模型确实让这套算法值钱了。** 线上优先走的 u2netp 显著度下，三个比例里算法保留率都高于居中裁剪
   （src 0.9777 vs 0.9751，1:1 0.9292 vs 0.9109，3:4 0.8775 vs 0.8642），而且差距主要来自构图：
   三分点距离比居中裁剪小 29%~36%（0.0982 vs 0.1543），摆正中的比例从 13% 掉到 3%。
   它平均只留 75% 的画面，却保住了 97.8% 的主体 —— 这就是"裁紧了，主体还在，而且更靠三分点"。
2. **规则兜底显著度是这条链路的短板。** 换成 `salienceFromArgb`，src 口径基本打平（0.9872 vs 0.9880），
   换比例时反而比居中裁剪差（1:1 −13.4%、3:4 −21.8%）；而且 66.5% 的图直接不裁了 ——
   规则图的峰值太弥散，`bestCrop` 那道"bestScore ≥ base + 0.05 才动剪刀"的门槛（`AutoFrame.kt:589`）
   过不去，算法等于没运行。**要提升自动构图，先提升兜底显著度，而不是改搜框逻辑。**
3. **"切到主体"这个数字会骗人，要看切了多深。** 模型口径下"切到主体"的比例从 22% 升到 31%，
   但损失分档一看，多出来的几乎全在 1%~5% 那一档：损失 >10% 的图反而比居中裁剪**少**（5.0% vs 8.0%），
   >20% 的只有 1.0%（居中 3.5%）。判据是"框内留下 < 99% 的主体像素"，掩膜边缘擦掉一点也算，
   所以单看这个比例会把算法判得比实际更粗暴。**换比例（1:1 / 3:4）才是真丢主体**：
   平均损失 7.1%/12.3%，居中基线同样丢 8.9%/13.6% —— 丢的是"换了画幅"这件事，不是"裁得不好"。
4. **胜率别单看。** model-src 败率 32.5% 高于胜率 14.0%，均值却仍占优：赢的图平均多留 11.5 个
   保留率点，输的平均只少留 4.2 个。只看命中率会误判这套算法"偏保守、动得少"。
5. **换比例（1:1 / 3:4）不如保持原比例稳。** 同样模型口径，src 的提升捕获 39.7%，
   3:4 只有 20.8%，切到主体的比例也高得多。产品上如果要给"方构图/竖构图"选项，
   最好让用户看到结果再确认。
6. **两个旋钮：动剪刀的门槛别改成相对口径，候选锚点可以放心砍到 12 个。** 前者实测更差
   （RANGE 0.10 的提升捕获 +1.0%），后者白拿 1.8 倍速、指标不动。默认值都还是旧行为，
   真要在端上启用，改的是调用方那一个参数。

## 局限（别把上面的数字用过头）

- DUTS-TE 是**显著性**数据集，掩膜标注的是"主体在哪"，不是"这张照片构图好不好"。
  它能证明"没把主体裁掉、主体摆得更靠三分点"，**证明不了照片更好看**。
- 200 张、单一数据集、没有跨数据集交叉验证；种子的抽样偏差没量化。
- 网格只有 64x48，框的宽高比与请求值最多差约 1%（网格量化）。算法、居中基线、最优上界都在
  同一套网格上取框，所以三方对比公平，但绝对值别当精确值读。
- harness 不处理 EXIF 方向（DUTS 图没有方向标记），也不走线上 `GRID_PEAK_GATE = 0.75` 那道
  "没主体就不另存"的闸；这批评测每张都有主体，那道闸不影响结论。
- 掩膜本身有标注噪声（边缘像素、细小主体），"切到主体"的 1% 容差也因此偏敏感。主体损失分布表就是
  为了把这个敏感度显式化：>1% 那列别单读，和 >10% / >20% 两列一起看。
- `avg_crop_us` 是单次 JVM 里 200 张图的平均，含 JIT 预热，只能做同一次运行内的相对比较
  （1002 µs vs 564 µs 是同一天同一台机器跑出来的）。
- `pack_pixels.py` 用 `PIL` 双线性缩放；端上用 `Bitmap.createScaledBitmap(..., true)`。
  大比例缩小时两者接近，但不是逐位一致。

## 第二指标：换个"眼睛"看——美学模型也说不出哪种裁法更好看

保留率、三分点距离都是几何指标，能证明"主体没被切掉、摆得更靠三分点"，证明不了照片变好看。
所以又接了两个在 AVA 上训过的美学打分模型，做同尺寸配对比较（算法框 vs 居中框）。

模型不入库，自己下（CPU 跑，onnxruntime，不需要 torch）：

| 模型 | 来源 | 大小 | AVA 排序相关 |
| --- | --- | --- | --- |
| TOPIQ-IAA ResNet50 | `cromsc/topiq-iaa-res50` → `topiq_iaa_res50.onnx` | 267 MB | PLCC 0.737 / SRCC 0.7359 |
| NIMA MobileNet | `cromsc/nima-mobilenet-aesthetic` → `nima_mobilenet_aesthetic.onnx` | 12.3 MB | 约 0.717（VGG16 版口径） |

```powershell
python tools/eval/export_crops.py --manifest <work>\manifest.tsv --harness <work>\harness_model_src.tsv --out-dir <work>\crops_trim --only-cropped
python tools/eval/aesthetic_score.py --pairs <work>\crops_trim\pairs.tsv --model-dir <模型目录> --models topiq,nima --full
python tools/eval/pref_eval.py --pairs <work>\crops_trim\pairs.tsv --scores <work>\crops_trim\scores_all.tsv --json <work>\crops_trim\pref.json --md <work>\crops_trim\pref.md
```

两模型合计 58 ms/图（TOPIQ 49.8 ms、NIMA 2.3 ms），140 对跑完 33 秒。
200 张里真正裁过的只有 140 对（`--only-cropped` 把"没动刀"的 60 张滤掉）。

结果（model-src 口径，140 对）：

| 模型 | 胜/平/负 | 平均分差 | 符号检验 p | 分差 σ | 95% CI |
| --- | --- | --- | --- | --- | --- |
| TOPIQ-IAA | 70/0/70 | −0.0059 | 1.0000 | 0.1287 | ±0.021 |
| NIMA MobileNet | 64/0/76 | −0.0083 | 0.3526 | 0.1260 | ±0.021 |

**两个美学模型都看不出算法裁剪比居中裁剪更好看。** 平均差 0.006~0.008 分（量程 1~10，约 0.1%），
远小于噪声下限。

- 符号不稳：只看前 40 对时 TOPIQ 是 +0.0117（算法赢），全量转负。这个量级的差异在 140 对里就是抛硬币。
